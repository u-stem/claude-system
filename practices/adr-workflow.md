# 意思決定記録(ADR)の運用

## 関連する原則

- [`principles/02-decision-recording.md`](../principles/02-decision-recording.md) — 判断の根拠を未来の自分・未来の AI が再構成できる形で残す。同原則の「連番文書」は判断本体(決定・根拠・退けた案)を指し、検証の経緯は変更履歴に置くと解釈する
- [`principles/01-context-economy.md`](../principles/01-context-economy.md) — 記録は読まれて初めて価値を持つ。読まれない記録は注意総量を消費するだけ
- [`principles/06-evolution-strategy.md`](../principles/06-evolution-strategy.md) — 不変層への手入れは MAJOR バージョンアップ相当として記録する

## いつ使うか(トリガー)

判断は 3 つの置き場に分けて残す。読まれる順に並べる。

1. **実物の隣**: 設定ファイルの注記、自動化スクリプトの冒頭コメント、共通指示の各節に置く 1 行の根拠。変更するときに必ず目に入る場所
2. **決定索引**: 現行の決定を 1 画面に集めた索引([`meta/decisions/README.md`](../meta/decisions/README.md))。各行は「決定 / 根拠 / 再評価トリガー / 退けた案 / 出典」。変更を計画するときはまずこれを読む。その場で編集する現在形の文書で、過去の状態は保持しない
3. **決定記録(ADR)**: 索引の 1 行に収まらない判断の記録。60 行以内

ADR を起票するのは次の 2 つの場合だけ:

- 設定や共通指示に落とし込めない方針判断(トレードオフの比較、機械的ガードレールの新設・撤去、セキュリティ・プライバシー方針の変更、破壊的書き換え)
- 索引にある決定を覆すとき

単純なバグ修正、typo、能力単位の追加、実物の隣の注記で足りる設定変更では書かない。判断が設定に落とし込めているなら、注記が ADR の代わりになる。優先順位は「覆す > 落とし込める」: 索引の既存行の決定を覆す変更は 1 行で書けても ADR を起票し、新しい行の追加やトリガー・退けた案の更新は注記 + 変更履歴 1 行で足りる。

## 手順

1. **索引を先に更新する**: 決定・根拠・再評価トリガー・退けた案を 1 行にする。1 行にできない判断だけ ADR に進む
2. **連番を採番する**: 直近の番号 + 1。欠番禁止、撤回しても番号は残す
3. **5 項目で書く**: 決定(何を)/ 根拠(3 行以内、各行末に所在を 1 つ添える: URL・ログのパス・比較したコマンド)/ 再評価トリガー(何が起きたら見直すか)/ 不採用と理由(1 案 1 行)/ 影響ファイル。任意で「覆す決定」「代償」。合計 60 行以内。Status は `Accepted` / `Proposed` / `Rejected` / `Withdrawn` のいずれか
4. **覆す決定を名指しする**: 索引の該当行と、根拠を持つ旧 ADR の番号を「覆す決定」欄に書き、索引の一覧の該当行にも注記する。覆した旧決定は索引の退けた案へ移す。旧 ADR は編集しない(凍結)。Status は起票時の状態で固定し、`Proposed` の判断は採択されるまで索引に載せない。「覆す」は決定本体を変えたときに限り、条件付き約束の撤回は再評価トリガー欄で「閉じた」と書く
5. **経緯は変更履歴へ**: 検証の顛末、途中の誤読と訂正、走査結果の表は ADR に書かず、変更履歴([`meta/CHANGELOG.md`](../meta/CHANGELOG.md))の 1 エントリに 40 行以内で残す。一次記録(ログ、会話の記録)は別に存在する
6. **将来の実行の約束は同じコミットで TODO へ転記する**: ADR や索引に「後でやる」と書いただけの約束は棚卸しに掛からず履行されない。転記しない約束は履行されないものとして扱う
7. **意思決定者の識別子規約を守る**: 本名・新規連絡先を書かない(ADR 0001)

## 判断基準

| 状況 | 置き場 |
|---|---|
| 設定値の変更で根拠が 1 行で書ける(既存の決定を覆さない) | 実物の隣の注記 + 索引の該当行 + 変更履歴 1 行(出典欄は `注記: <ファイル>` か `CHANGELOG YYYY-MM-DD`) |
| 索引の決定を覆す | ADR(覆す決定を名指し)+ 索引の更新 |
| 機械的ガードレールの新設・撤去 | ADR + 索引 |
| セキュリティ・プライバシー方針の変更 | ADR + 索引 |
| 破壊的書き換え | ADR + 索引 |
| 単純なバグ修正・typo・能力単位の追加 | コミットメッセージ / 変更履歴 |
| 検証の経緯、訂正の記録 | 変更履歴の 1 エントリ |

迷ったら「3 年後の自分に聞かれて答えられるか」で書くかを決め、「次に変更するときに読み返すか」で置き場を決める。読み返さない記録は書かない。

## アンチパターン

- 判断の物語を ADR に書く(検証の逐語、途中の誤読、走査表)。読まれないうえ、記録済みの方針を前提の再検証なしに拘束条件として扱わせる
- 索引を更新せず ADR だけ増やす(現行方針が 1 か所で読めなくなる)
- 旧 ADR の Status や本文を編集して現行状態を表そうとする(履歴と現在が混ざり、変更のたびに古い記録を触る作業が生まれる)
- 実物の隣に書ける根拠を離れた文書に書く(変更するときに目に入らない)
- 退けた案を残さない(後で同じ案を再提案する)
- 番号を飛ばす、個人特定情報を書く、Public な記録から Private リソースへの URL を貼る(ADR 0001 / 0002 違反)

## 旧資産からの継承

旧資産には独立した意思決定記録の運用は存在せず、変更履歴と運用方針が同居していた。本 practice は ADR 形式を導入して 26 本・313KB に達した時点で「物語が判断を妨げ、古い記録の保守が判断を再燃させる」と運用者が認めたことを受け(2026-09-06)、索引と実物の隣を一次の置き場とし ADR を短い記録に限定する形に改めたもの。
