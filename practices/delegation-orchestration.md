# 委譲とオーケストレーションの規律

司令役(メイン)は指示出しと統合に徹し、実作業と大量の中間出力は独立コンテキストを持つ委譲先に閉じ込める。
この役割分離が、注意の有限性([`principles/01-context-economy.md`](../principles/01-context-economy.md))を運用に落とす最も効く手段の一つである。

## 関連する原則

- [`principles/01-context-economy.md`](../principles/01-context-economy.md) — 委譲はメインの注意を保つための経済的選択
- [`principles/03-skill-composition.md`](../principles/03-skill-composition.md) — 1 単位 1 責務、能力の合成
- [`principles/05-separation-of-concerns.md`](../principles/05-separation-of-concerns.md) — 役割境界と最小権限

## いつ使うか(トリガー)

委譲を既定とするのは、以下のいずれかに該当するとき:

- **広範な探索**: 5 クエリ超、または 10 ファイル以上の横断が見込まれる
- **大量出力の予測**: 結論に対して中間出力が支配的になる(ログ走査、全文読解、一括変換)
- **独立並列タスク**: 相互依存のない複数サブタスクがある(同時に走らせて束ねられる)

逆に、既知の 1 点(特定ファイル・シンボル・値)の参照だけで済む単発の小タスクは、委譲せずメインで直接実行する。委譲自体にも固定費(往復・指示の編成)がかかるため、利得が固定費を上回る場合にのみ委譲する。

## 手順

1. **役割を分ける**: メインはタスク分解・委譲先選定・結論統合・不可逆操作の判断・対話を担う。委譲先はスコープ内の実作業と中間出力の消化を担う。
2. **スコープを絞って渡す**: 生のコンテキストを丸投げせず、目的・制約・対象範囲を絞ったタスク記述を渡す。
3. **返却の形を先に決める**: 委譲先には「何を、どの構造で返すか」を指定する。返りは構造化された結論(要点 + 位置参照)に限り、ファイル全文・探索ログ・中間出力をメインへ戻させない。
4. **並列の束ね方を選ぶ**: 全結果が揃って初めて意味を持つ場合のみ待ち合わせる。逐次依存のない段は待ち合わせず、各タスクを独立に流す。
5. **段階を上げるのは明示要求時のみ**: 多段・多数の委譲先を決定論的に束ねる重い仕組みは、利用者の明示的な要求があるときだけ起動する(コストが大きいため自動起動しない)。
6. **結論だけ統合する**: メインは戻ってきた構造化結論を統合し、次の判断に使う。中間生成物はメインのコンテキストに載せない。

## 連鎖(委譲のチェーン)

単発の委譲では足りず、複数の役割を順序立てて連ねたい場面がある(例: 計画 → 反証 → 実装 → レビュー → 最終確認)。このとき守る規律:

1. **連鎖は必ず司令役を経由する単層構造にする**。委譲先は自ら別の委譲先を起動しない(再委譲しない)。各段の結論は必ず司令役に戻り、司令役が次の段へ渡す。多段の入れ子(委譲先がさらに委譲する)に依存した設計にしない。
2. **段の取捨選択は司令役がタスクの性質で判断する**。標準の並び(探索 → 計画 → 反証 → 実装 → レビュー → 最終確認 → 文書追従)を起点に、不要な段は飛ばす。役割を固定テーブルで強制しない([`principles/03-skill-composition.md`](../principles/03-skill-composition.md) の 1 単位 1 責務と合成)。
3. **判断と実作業の担当を分ける**。計画・反証(判断材料の生成)と、実装・適用(変更の実行)を別の委譲先に割り当て、独立性を保つ。反証は重い・不可逆な判断の直前に挟む。
4. **各段の入出力を構造化する**。前段の構造化結論を次段の入力に整形するのは司令役の責務。中間生成物を素通しで次段に流さない。

連鎖の固定費(段ごとの往復)は単発より大きい。設計級・不可逆級の作業で連鎖の利得が固定費を上回るときに使い、軽微・可逆な作業は単発委譲か司令役の直接実行で足りる。

## 委譲ファースト(原則委譲・例外直接)

実作業(探索・計画・反証・実装・レビュー)は**原則として対応する委譲先に委ねる**のを既定とする。司令役は分解・選定・統合・不可逆操作の判断に集中する。
ただし**軽微・可逆・1 点参照**の作業は委譲の固定費が利得を上回るため司令役が直接実行してよい。「必ず委譲」を機械的に全作業へ適用しない(損益分岐を壊す)。この線引きは上記「いつ使うか」「判断基準」のトリガーに従う。

## 判断基準

| 状況 | 委譲する | メインで直接 |
|---|---|---|
| 広範な探索(5 クエリ超 / 10 ファイル以上) | ◯ | |
| 中間出力が結論より大きいと予測 | ◯ | |
| 独立タスクが複数ある | ◯(並列) | |
| 既知の 1 点参照・軽微な確認 | | ◯ |
| 結論統合・不可逆操作の判断・対話 | | ◯(メインの責務) |

返却フォーマットを指定できないほどタスクが曖昧なら、まず曖昧さを解消する(委譲しても構造化結論が返らない)。

## アンチパターン

- 委譲すべき広範な探索をメインで実行し、中間出力でメインのコンテキストを肥大させる
- 委譲したのに、委譲先が全文・ログをそのままメインへ返し、圧縮の利得を失う
- 返却の構造を決めずに委譲し、メイン側で再パース・再判断が発生する
- 固定費を無視して、1 点参照の小タスクまで委譲する(往復が純損)
- 待ち合わせ不要な段で全結果を待ち、速い委譲先を遊ばせる
- 重いオーケストレーションを明示要求なしに自動起動し、コストを膨らませる

## 旧資産からの継承

旧資産では「探索は別コンテキストへ委譲」「単発の小タスクは直接実行」「5 クエリ・10 ファイルの目安」が個別 heuristic として点在していた。本 practice はそれらを「メイン=司令役 / 委譲先=実作業」という役割分離の規律として束ね、渡す情報と返却の構造まで含めた運用手順にまとめたもの。
